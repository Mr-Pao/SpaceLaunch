# SpaceLaunch 静态数据部署说明

## 一、这套方案在做什么

小程序不再请求海外 API，也不依赖云函数和数据库。数据流变成：

```
GitHub Actions（海外节点，定时跑）
        │  每 15/30/60 分钟 抓 LL2
        │  历史归档：每小时 8 页，断点续传（archive.yml）
        │  译文回填：不碰 LL2，只读 COS + 调翻译接口（backfill.yml）
        ▼
  精简 JSON（裁剪后约 10–60 KB）
        │  COS 上传
        ▼
  对象存储 + CDN（国内节点）
        │  uni.request
        ▼
  小程序（Storage 缓存优先渲染，后台静默刷新）
```

关键收益：

| 指标 | 旧架构（EMAS 云函数） | 新架构（静态快照） |
|---|---|---|
| 首屏耗时 | 冷启动 1–2 s + 数据库查询 | 有缓存 0 ms / 无缓存 80–200 ms |
| 数据延迟 | 每小时一轮，且 `detailed` 模式实测超时 | 15 分钟一轮，可控 |
| 月成本 | 5 元起（云函数有小时级低消） | 约 0 元 |
| 下线风险 | EMAS 2027-09-30 停服 | 无厂商锁定 |

## 二、请求预算

LL2 未认证限额 **15 次/小时**。当前分配：

| 数据集 | 频率 | 请求/小时 |
|---|---|---|
| 即将发射 `launches/upcoming` | 每 15 分钟 | 4 |
| 事件 `events/upcoming` | 每 60 分钟 | 1 |
| 历史发射 `launches/previous` | 每 60 分钟 | 1 |
| **历史归档**（offset 逐页） | 每小时 8 页，断点续传 | 8 |
| 机构 `agencies` | 每天 1 轮（4 页） | ≈0.17 |
| 即将发射后续排期 `upcomingMore` | 每天 1 轮（4 页） | ≈0.17 |
| 火箭型号库 `launchers` | 每天 1 轮（6 页，detailed） | ≈0.25 |
| 统计 `stats` | 每天 1 轮 | **0**（不请求 LL2，读 COS 上的快照与归档） |
| 译文回填 `backfill` | 每 15 分钟 | **0**（只读 COS + 翻译接口） |
| **合计** | | **≈14.6** |

余量已经很薄（限额 15）。所以：

- 统计与回填刻意做成**不碰 LL2**，把额度全留给真正需要抓的数据；
- 归档页数是**按实际间隔自适应**的（8 页/小时，上限 24 页），
  漏一小时就下轮补回来，不会因为定时不准就永久少数据。

**注意：限额是按 IP 计的，本地调试会消耗你自己的额度**，反复跑脚本很容易触发 429
（实测报错 `Request was throttled. Expected available in 1096 seconds.`，要等约 18 分钟）。

所以本地调试请一律加 `--base=dev` 走开发端点（见第四节），正式端点只留给 CI。

如果后续想提高刷新频率，去 https://thespacedevs.com/llapi 申请免费 API token，
填到 GitHub Secret `LL2_TOKEN`，脚本会自动带上，限额会宽松很多。

> 一个容易误判的点：即使桶是公有读，**匿名访问桶根（列目录）仍然返回 403 AccessDenied**。
> 公有读只给 `GetObject`，不给 `ListBucket`。所以判断桶权限不能看根路径，
> 要看具体对象：对象存在则 200，不存在则 404 `NoSuchKey`（而不是 403）。

代码里额外给对象打了 `public-read` ACL（`COS_ACL` 环境变量），属于冗余保险：
整桶哪天被改回私有，上传的文件依然可读。想省掉这一步，删掉 workflow 里的 `COS_ACL` 即可。

实测 4 个文件匿名访问全部 200，耗时 67–223 ms。

如果要消掉控制台上那个「高风险」标签，可以改成桶策略只开放这一个目录：

- 桶 → 权限管理 → 存储桶访问策略 → 添加策略，
  授权对象 `*`，资源写 `spacelaunch-1258113633/space-data/*`，操作只勾 `cos:GetObject`
- 然后把桶的访问权限改回「私有读写」

不影响小程序，纯粹是把公开范围收窄。

不需要开静态网站功能，直接走对象地址即可。

### 三条流水线（四·补充）

| workflow | 干什么 | 频率 | 占 LL2 配额 |
|---|---|---|---|
| `sync.yml` | 抓四/五个数据集 → 中文化 → 镜像图片 → 上传 | 每 15 分钟 ~ 每天 | 是（≈7/h） |
| `archive.yml` | 历史发射全量归档（offset 逐页，断点续传） | 每小时 4 个点（5/20/35/50 分） | 是（8/h） |
| `backfill.yml` | 给归档分片补中文（只读 COS + 翻译接口） | 每 15 分钟 | **否** |

归档的四个要点：

1. **断点在 COS 上**（`space-data/history/state.json`），CI 容器每次都是新的，
   状态只能存在外面。索引另存一份 `index.json` 给前端读，不暴露内部字段。
2. **页数按实际间隔自适应**（8 页/小时，上限 24 页，最小间隔 9 分钟），
   定时漏几小时也不会少抓 —— 下一轮按间隔一次补回来。
   定时点是 `5,20,35,50` 每小时 4 个：单次投递率不到 100%，点多才扛得住漏。
3. **不翻译**：800 条 × 每条约 1.5 秒会顶破 CI 时间上限，译文交给 backfill 慢慢补。
4. **全量抓完后转维护模式**：新发射会把 LL2 列表整体下推，头部会留一道空缺，
   维护模式每次重抓最新 4 片补上；重写前会按 id 把已回填的中文搬回来，避免冲掉 backfill 的成果。

手动推进（想快点补完时）：Actions 页面 → `archive-history` → Run workflow →
`pages` 填 24（单轮上限）。

## 五、GitHub Actions 的三个坑

**1. cron 不准时，而且会漏。** GitHub 的定时触发常态延迟 5–15 分钟，高峰期更久，
实测还会**整点漏投递**（本仓库新建一个每小时任务后，连续两小时一次都没跑；
而 `*/15` 那个因为点密，记录明显更多）。所以：

- 不要把刷新频率设得比 15 分钟更密，也没有意义；
- **依赖定时推进的任务要能自愈**：归档脚本按「距上次更新时间」折算页数，
  漏几小时也不会少抓；归档还排了两个 cron 点（5 分 / 35 分）互为备份；
- 改完脚本想立刻验证，用 **push 触发**（即时），别等定时。

**2. 60 天无提交会被停用。** 公开仓库连续 60 天没有新提交，所有定时 workflow
会被自动禁用，而且**不通知你**。workflow 里已加保活步骤：距上次提交超过 45 天
就补一个空提交。如果发现仍未生效（`GITHUB_TOKEN` 推送是否计入活跃度存在争议），
退路是每两个月去 Actions 页面点一次 "Enable workflow"。

**3. 抓取本身很慢。** 实测 `launches/upcoming?limit=50&mode=normal` 在国内网络
需要 27 秒到 120 秒以上，晚间高峰期会直接超时。这正是要用 GitHub 海外节点的原因。
脚本超时设的是 120 秒，单次 workflow 上限 15 分钟，够用。

## 八、已知的坑（改造时实测出来的）

1. **`mode=detailed` 必须禁用**：实测 72 秒超时，`mode=normal` 才 27 秒，且页面要的字段 normal 全都有。
2. **火箭参数的正确端点是 `/launcher_configurations/`（带下划线），且必须 `mode=detailed`**。
   `/config/launcher/`、`/configurations/`、`/rocket-configurations/`、`/vehicles/` 全是 404。
   旧云函数里这条一直是坏的，导致早期误判「LL2 没有型号数据」。
   这是全项目**唯一**用 detailed 的地方，其余一律 normal。
3. **图片字段的真实名字不是 `image_url`**：
   - 发射：`launch.image` 是对象 `{image_url, thumbnail_url, ...}`
   - 活动：字段是 `event.image`（对象），**不是 `feature_image`**。读错的结果是活动列表 29 条全部无图
   - 机构：字段是 `agency.image` 和 `agency.logo`（对象或 null），**根本没有 `image_url` / `logo_url`**
   
   这解释了为什么旧版小程序里机构图和活动图从来没显示过。
4. **`agency.founding_year` 是数字**（如 `1960`），只判断字符串会得到空值，"成立时间"永远空白。
5. **`agency.launchers` 是字符串**（`"A | B"`，空值为 `""`），不是数组；`agency.country` 才是数组。
6. **详情页不能传下标**：列表刷新后下标会错位，要传 `id`。
7. **`navigationStyle: custom` 没有返回按钮**：旧配置所有页面都是 custom，
   详情页进去出不来。现已改为默认导航栏。
8. **`<text>` 里不能嵌自定义组件**：`<text><uni-dateformat/></text>` 在微信端不渲染。
9. **uview-ui 2.0.34 与 Vue3 完全不兼容，已整体摘除**（两个坑连着踩）：
   - **编译期**：`libs/mixin/mixin.js` 用 `module.exports = {}`（CommonJS），
     而 `index.js` 用 `import mixin from` 引入，Vite 报
     `"default" is not exported by "libs/mixin/mixin.js"`。
   - **运行期**：`index.js` 的 `install` 是纯 Vue2 写法——
     `Vue.filter(...)`、`Vue.prototype.$u = $u`、`Vue.mixin(mixin)`。
     Vue3 的 app 实例没有 `filter` 方法，`app.use(uView)` 直接抛
     `Vue.filter is not a function`，app.js 启动失败，连带出现
     `Page "pages/index/index" has not been registered yet`。
   - **处理**：已注册的 6 个页面里 `u-*` 组件出现 **0 次**，所以从 `main.js` 去掉
     `import uView` / `app.use(uView)`，同时去掉 `App.vue` 与 `uni.scss` 里的 uview 样式导入，
     省下约 250KB。
   - **将来若需要 Vue3 组件库，用 uview-plus**（uview 的 Vue3 分支），不要再装回 uview-ui。
   - 残留：`pages.json` 的 easycom 里还留着 `^u-(.*)` 规则、未注册的
     `pages/upcoming/upcoming.vue` 里还 import 了 uview 的 `colorGradient`。
     两者都不参与编译（该页面未注册），不影响运行。
10. **HarmonyOS 兼容性警告是误报**：`components/thorui-nvue/.../bridge-weex.js` 里有
    `navigator.userAgent` 判断，编译器提示"可能未适配鸿蒙"。这段代码属于未使用的
    thorui-nvue 组件，不参与打包，可以直接忽略。

## 九、编译运行（HBuilderX）

**微信开发者工具不能直接打开这个项目。** 它只认 `wxml / wxss / js / json` 四种原生文件，
而本项目是 `.vue` + `pages.json` + `uni_modules/`，必须先经 uni-app 编译器转换。

### 为什么必须装 HBuilderX

这是 **HBuilderX 项目**，不是 CLI 项目，判断依据：

- 存在 `.hbuilderx/launch.json`
- `manifest.json` 里有 `"appid": "__UNI__C1A5695"`
- 根目录没有 `vite.config.js`、没有 `@dcloudio/*` 依赖

所以默认只能靠 HBuilderX 编译。（另一条路是改造成 CLI 项目用 `npm run dev:mp-weixin`，
但要对齐 `@dcloudio` 一堆版本号，成本更高。）

### 安装

1. 打开 https://www.dcloud.io/hbuilderx.html → 点下载
2. 选 **正式版** → **Windows** → **标准版**（zip 压缩包，**免安装**，解压即用）
   - 不需要「App开发版」：那个多了 App 真机运行和云打包，本项目只发小程序
3. 解压到任意目录，双击 `HBuilderX.exe`

### 首次运行

1. HBuilderX → 菜单 **文件 → 打开目录** → 选项目根目录（含 `pages.json` 的那一层）
2. 首次会提示安装**编译插件**，点确定让它自动装（标准版默认不带 uni-app 编译器）
3. 编译时会提示安装 **scss/sass 编译插件**（`uni.scss` 和 `App.vue` 里用了 scss），同样点确定
4. 菜单 **运行 → 运行到小程序模拟器 → 微信开发者工具**
5. 首次会让你指定微信开发者工具的安装路径（`微信开发者工具.exe` 所在目录）
6. 微信开发者工具启动后，若报域名错误：**详情 → 本地设置 → 勾选「不校验合法域名」**

编译产物在 `unpackage/dist/dev/mp-weixin/`，也可以直接用微信开发者工具打开这个目录。

### 编译相关的小设置

- `.hbuilderx/launch.json` 的 `mp-weixin.launchtype` 已从 `remote` 改为 `local`，
  默认走本机微信开发者工具，而不是远程调试。
- 根目录原有一个 `package.json`（内容是 Flip-Countdown 插件元数据，带 `dcloudext` 标记，
  还有 `laf-client-sdk` 依赖），与项目无关，已改名为 `package.json.flip-countdown.bak`，

  HBuilderX 能正常解析。**不要当成错误去删注释。**
