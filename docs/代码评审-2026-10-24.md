# SpaceLaunch 全量代码评审

日期：2026-10-24　方式：静态通读 + 线上数据实测（COS 上 7 个数据集体积、归档状态、CI 运行记录）
结论：**只分析不改动**，等你确认后再决定动哪些。

## 一、架构与模块职责

整体是「CI 侧生产静态 JSON → COS 分发 → 小程序纯消费」，没有云函数、没有数据库，这点非常克制，继续保持。

### 数据生产侧（Node / GitHub Actions）

| 模块 | 职责 | 关键文件 |
|---|---|---|
| 同步 | 抓 LL2 → 裁剪 → 中文化 → 图片镜像 → 上传 COS | `scripts/sync.js`（DATASETS 表驱动） |
| 归档 | 历史 7656 条按 offset 分页断点续传 | `scripts/archive.js` |
| 回填 | 给归档分片补中文（不碰 LL2） | `scripts/backfill.js` |
| lib | HTTP 封装 / 字段裁剪 / 翻译 / 图片压缩 / COS / 按年聚合 | `scripts/lib/{fetch,slim,translate,image,cos,aggregate}.js` |
| 工作流 | 三条流水线，cron 到数据集的映射 | `.github/workflows/{sync,archive,backfill}.yml` |

### 数据消费侧（uni-app / Vue3）

| 模块 | 职责 | 关键文件 |
|---|---|---|
| 数据层 | 三级缓存（内存 → Storage → CDN）+ 按 id 查找 | `utils/data.js` |
| 格式化 | 时间/状态/火箭中文名/标题拼装 | `utils/format.js` |
| 列表复用 | 数据获取 + 本地分页 + 收藏置顶 | `utils/list-mixin.js` |
| 历史分片 | 读归档索引与分片 | `utils/history.js` |
| 页面 | 5 个 tab 页 + 详情 4 页 | `pages/**` |
| 组件 | 卡片 / 倒计时 / 导航条 / 首页大卡 | `components/**` |
| tabBar | 悬浮胶囊（原生 wxml/wxss） | `custom-tab-bar/*` |

|---|---|---|
| `launches-upcoming.json` | 174 KB / 100 条 | ≈1.7 KB 每条，描述字段占大头 |

## 二、潜在 bug 与风险点

### P0 —— 用户直接能撞上，建议优先修

**1. `pages/index/index.vue` 用了 `spaceData` 却没 import**
位置：`pages/index/index.vue:196`（`loadMoreUpcoming()` 里 `spaceData.load('upcomingMore')`）
现象：首页滑到底触发 → `ReferenceError: spaceData is not defined` → 被 `catch` 吞掉只留一条 console.warn
→ **「上拉加载后续排期」永远不生效，且没有任何报错提示**。与之前反馈的「首页加载更多好像没起作用」完全吻合。
风险：静默失效，很难自查。同类页面（previous / rockets / stats）都正常 import 了，只有首页漏了。

**2. 历史发射的详情页打不开**
位置：`utils/data.js:285` `findLaunchById()` 只扫描 `['upcoming','previous']` 两个数据集
现象：`pages/previous/previous.vue` 从第 101 条起的数据全部来自归档分片，点进去 → `findLaunchById` 两个数据集都没有 → `detail = null` → 页面显示「未找到该发射任务」。
影响面（同一根因，三处入口）：
- 已发射列表第 101 条之后 —— **每一条都点不开**（`previous.json` 只装最新 100 条，
  第 101 条起全部来自归档分片，而 `findLaunchById` 不查分片）；
- 统计页「失败 / 部分成功复盘」里**落在归档分片内的那些**（即不在最新 100 条里的）→ 点不开；
- 收藏的历史任务点进去 → 同样。
这是当前功能链上最大的断点：历史数据拉下来了、也显示出来了，但点不进去。
（归档全部补完后，7656 条里有 7556 条都会落到这个坑里。）

### P1

**3. Storage 写满时的 `clear()` 会连带清掉全部数据集**
位置：`utils/data.js:107` `writeStorage()` → 失败后调用 `clear()` 清空**所有** key
风险：写缓存失败时把首页数据也清掉，下次冷启动直接白屏等网络（首屏体验从 0ms 退化到网络往返）。
建议：只清最老 / 最大的 key（如 launchers、agencies、upcomingMore），保留 upcoming。

**4. tabBar 配置分散在三处**
位置：`pages.json` 的 `tabBar.list`、`custom-tab-bar/index.js` 的 `data.list`、`custom-tab-bar/index.wxml`
风险：改一个入口要同步三处，图标路径或顺序一旦不一致，tab 与页面就错位。
建议：以 `pages.json` 为唯一真源，`custom-tab-bar/index.js` 里改为读取（或至少加 CI/脚本校验）。

**5. 版本不一致**
位置：`manifest.json` 的 `versionName: 1.1.0` / `versionCode: 110` vs `utils/changelog.js` 里的 3.0/3.1
风险：HBuilderX 上传用的是 manifest，提审材料与用户看到的版本记录对不上。

**6. 归档依赖 offset，数据会整体漂移**
位置：`scripts/archive.js`（offset 分页）
现状：前端按 id 去重（`previous.vue` / `list-mixin.appendMore`）能兜住重复；新发射会在**头部**留一道空缺，
已在本次修复中加入维护模式（每次重抓最新 4 片）来补。风险已可控，但要记住：
**归档全部完成后如果维护模式没跑起来，头部空缺会逐年扩大**。

**7. 图片流量**
位置：`components/launch-card` 每张卡片 200rpx 缩略图
现状：`lazy-load` 已开，缩略图已压到 ≤30KB。但已发射页一旦翻很多页，累计请求数不小。
建议：观察 COS 流量账单；若压力大，归档分片可以不镜像图片（老任务的图访问频率很低）。

### P2（体验/细节）

8. `utils/format.js:49` `relativeTime()` 天数用 `Math.round` → 「1 天前」实际可能是 1.6 天前（应 `Math.floor`）。
9. `pages/rocket/rocket.vue:119` 显示「发射记录来自小程序缓存的最近 100 次」—— 文案诚实，但功能上只能看到最近 100 条内的记录，与「历史归档」能力割裂（与 P0-2 同源）。
10. `components/countdown` 的 `cd-sm` 样式无人使用（两处调用都传 `size="lg"`）。
11. `pages/previous/previous.vue` 的 `onShow` 只同步 tabBar，没有刷新收藏态；从详情页收藏返回后列表标记不更新（首页有 `reorder()`，历史页没有）。
12. 注释过时（误导性大于缺失）：
    - `utils/data.js:54` FILES.stats 仍写「最近 400 次发射的极简字段」→ 实际是按年预聚合；
    - `scripts/sync.js:144-150` 一大段旧方案注释（"拉最近 400 次"）**位置还挂错了**，夹在 launchers 数据集上方；
    - `scripts/lib/aggregate.js:22-25` 说历史分片用 `slimStatLaunch`，实测 `archive.js` 用的是 `slimLaunch`
      （`normalize()` 兼容两种所以没炸，但注释是错的）。

## 三、性能与可维护性建议

### 性能

1. **删掉「前端从不渲染」的字段（收益最直接）**
   逐个字段量过 `launches-upcoming.json`（163 KB / 100 条）：

   | 字段 | 占 JSON | 前端是否使用 |
   |---|---|---|
   | `mission`（名字+描述+类型+轨道+两种中文） | 43 KB | 用 |
   | `pad`（名称+经纬度+**map_image**+位置名） | 23 KB | 名称/位置/经纬度用，**map_image 从未渲染** |
   | `rocket` | 11.5 KB | 用 |
   | `image` | 8.4 KB | 用 |
   | `status` / `id` / `provider` / `name` | 各 3-6 KB | 用 |
   | `last_updated` | 2.2 KB | **前端 0 处使用** |
   | `location_launch_attempt_count(_year)` | 0.9 KB | **前端 0 处使用**（详情页只展示 orbital / agency / pad 三个计数） |

   其中 **`pad.map_image` 是纯浪费**：它不只占 9KB 的 JSON 体积，
   更要命的是 CI 每次同步都要为它下载 + 压缩 + 上传一遍
   —— upcoming 每 15 分钟 100 张、upcomingMore 每天 376 张，而这些图页面上从来没有出现过。
   建议：从 `slim.js` 移除 `pad.map_image`、`last_updated`、`location_launch_attempt_count(_year)`，
   并从三个数据集的 `images: [...]` 里删掉 `pad.map_image` 的镜像配置。
   预期 upcoming 163 KB → 约 148 KB，且 **CI 单次同步的图片处理量直接砍掉一半**（卡片外的图只剩 image 与 infographic）。

   若要进一步瘦身，再考虑描述截断：描述只占 20.5 KB（13%），收益不如上面三项。
2. **Storage 分级缓存**：`launchers`(435KB) / `agencies`(180KB) / `upcomingMore`(626KB) 访问频率远低于首屏，
   可单独设更短的 HARD_TTL，或只缓存首屏用得上的数据集，避免 1.6MB 长期占着 Storage。
3. **首页星空动画**：`pages/index/index.vue` 一次性生成 36 个 `.stars` view 并各带 2.4s 无限动画。
   建议减到 18 个，或改成一张静态星空底图（低端机上 36 个动画图层是实打实的合成开销）。
4. **首页加载动画用 setInterval 改 data**（50ms 一次 Vue re-render）：改成 CSS `@keyframes` 更省。
5. **stats 预聚合是对的**，继续保持这个思路：凡是「前端只需要聚合结果」的场景，都放到 CI 算。

### 可维护性

6. **列表页逻辑不统一**：`index` / `event` 用 `list-mixin`，`previous` 因为要接归档分片自己实现了一份
   （多出 `loadError`、`hasArchive` 等）。建议把「触底 + 归档分片」抽进 mixin 的 optional 能力，
   或至少让 `previous` 复用 `getData/applyData/refeshFav` 部分。
7. **HTTP 逻辑两份**：`scripts/lib/fetch.js` 有 `getJson`（带重试、区分 429），
   `scripts/archive.js` 又自己写了 `getJsonWithRetry`。建议统一到 `lib/fetch.js`，
   把「退避重试 + 间隔」做成参数。
8. **常量分散**：`DATA_VERSION` 在 `utils/data.js` 与 `scripts/sync.js` 各一份（必须同步，已踩过）；
   归档分片里的 `v: 6` 是另一套版本号，语义不同但名字一样，容易混。建议归档版本改名 `AV` 或干脆去掉。
9. **单测/验证脚本缺失**：`scripts/verify-slim.js` 是唯一一个，且会消耗正式配额。
   建议给 `aggregate.js` / `format.js` 这类纯函数补几个不联网的断言脚本（本次给 archive 加的
   `--dry` 干跑模式就是这个思路，可以推广）。
10. **死代码清理**（逐个确认后删）：
    - `utils/favorites.js` 的 `list / count / remove / clear`（没有收藏页，只有 `snapshot/has/toggle` 在用）
    - `scripts/lib/image.js` 导出的 `mirrorOne / summary / MAX_BYTES`（外部无人用）
    - `scripts/lib/slim.js` 导出的 `imageUrl / joinNames / statusZh / STATUS_ZH`
    - `components/countdown` 的 `cd-*` 小号样式
    - 根目录 `.hbuilderx/launch.json`、`package.json.flip-countdown.bak`（与 `docs/部署说明.md` 记录冲突时需确认）

## 六、建议的执行顺序

1. **先修 P0**（R2 + R1）：这两个是功能链真的断了，其它优化都建立在它们之上。
2. **再做 F1 / F2 / F6 / F11**：纯前端、低风险、用户感知强。
3. **然后 R3 / R5 / R6 / R8**：重构与包体瘦身，需要一次完整回归。
4. **最后 F4 / F5 / F9 / F10**：按兴趣挑，注意每个都要算一遍「新增数据集 → 配额」这笔账。

配额是硬约束，任何新增数据集都要先回答「多久刷一次、一次几个请求」。
